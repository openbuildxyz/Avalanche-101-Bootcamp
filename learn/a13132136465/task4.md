# 从 Swap 到借贷与衍生品——DeFi 的发展进程研究

## ① 定位：我们做的 Swap 在 DeFi 里是哪一环

这次课程中，我们实现的是一个简单的去中心化交易应用（DEX），核心功能是 Token 之间的即时交换，也就是 Swap。从 DeFi 的整体发展来看，Swap 可以说是最基础的一层金融基础设施：**先解决资产如何自由交换，之后才能进一步发展借贷、杠杆和衍生品。**

传统交易所通常使用订单簿（Order Book）来撮合买家和卖家。例如，一个人愿意用 10 美元买入 Token，另一个人愿意用 10 美元卖出，交易所将双方进行撮合。

而我们课程中使用的 DEX 更接近 AMM（Automated Market Maker，自动做市商）的思路。AMM 不一定需要等待某个具体的卖家出现，而是让用户直接和流动性池中的资产进行交易。

例如，一个 DLK/USDT 流动性池中有：

* 1000 DLK
* 10000 USDT

那么智能合约可以根据池子中两种资产的数量自动计算交换价格。

经典的 Uniswap AMM 使用恒定乘积公式：

```text
x × y = k
```

其中：

* `x`：池子中 Token A 的数量
* `y`：池子中 Token B 的数量
* `k`：池子的恒定乘积

当用户用 USDT 买入 DLK 时，池子中的 USDT 增加，DLK 减少。为了尽量保持 `x × y = k` 的关系，DLK 的价格会自动上升。因此，大额交易会产生更明显的价格影响（Price Impact）。Uniswap 的 AMM 正是通过流动性池和固定公式实现无需传统订单簿的自动交易。

因此，我们课程中的 Swap 可以理解为 DeFi 的第一层：

```text
Token
  ↓
DEX / AMM
  ↓
资产可以自由交换
  ↓
借贷、杠杆、衍生品等更复杂金融协议
```

没有方便的链上交易和流动性，后面的 DeFi 金融产品也很难发展。

---

## ② 梳理：DeFi 的发展进程

我理解 DeFi 的发展过程并不是简单地“出现了越来越多的协议”，而是不断把传统金融中的功能拆分成智能合约。

### 第一阶段：DEX 和 Swap

代表协议：Uniswap

早期 DeFi 首先解决的问题是：**如果没有中心化交易所，用户之间如何交易 Token？**

Uniswap 使用 AMM 和流动性池解决了这个问题。用户不需要把资产交给交易所托管，也不需要依赖传统订单簿，而是直接调用智能合约完成交易。

同时，普通用户也可以向流动性池提供两种 Token，成为 LP（Liquidity Provider，流动性提供者），并获得交易手续费收益。

这一阶段建立了 DeFi 最重要的基础：**链上资产的自由交换和流动性。**

---

### 第二阶段：去中心化借贷

代表协议：Aave

有了 Token 和流动性之后，DeFi 开始解决第二个问题：

**用户能不能把暂时不用的资产借给别人，同时获得利息？**

这就是去中心化借贷协议。

以 Aave 为例，用户可以将资产存入协议中形成资金池，其他用户在满足抵押条件的情况下可以从资金池借出资产。

例如：

```text
Alice 存入 10 ETH
        ↓
作为抵押品
        ↓
借出一定数量的 USDT
```

与传统银行不同，链上借贷通常不依赖身份证、信用记录或人工审核，而主要依靠**超额抵押（Overcollateralization）**。

也就是说，用户借 1000 USDT，可能需要抵押价值 1500 USDT 或更多的 ETH。

这样做的原因是区块链上的用户通常是匿名地址，协议无法像银行一样判断用户是否有偿还能力，因此必须通过抵押资产来降低风险。

Aave 使用 Health Factor（健康因子）衡量借款仓位的安全程度。当抵押物价值下降，导致健康因子低于安全阈值时，仓位可能进入清算。清算人偿还部分债务，并获得借款人的部分抵押品以及清算奖励。

这一阶段让 DeFi 从“交易资产”发展到了“让资产产生利息”。

---

### 第三阶段：杠杆交易和衍生品

代表协议：dYdX

当链上已经具备交易、借贷和价格体系后，更复杂的金融产品开始出现，例如：

* 杠杆交易
* 永续合约
* 期货
* 期权
* 其他衍生品

dYdX 是去中心化衍生品领域的重要代表之一。永续合约允许用户不直接持有 ETH 或 BTC，也可以通过合约获得对应资产价格上涨或下跌的收益。

例如：

```text
用户认为 ETH 会上涨
        ↓
存入 USDC 作为保证金
        ↓
开 ETH Long 仓位
        ↓
ETH 上涨 → 获利
ETH 下跌 → 亏损
```

与普通 Swap 最大的区别是：

**Swap 是直接交换资产，而永续合约交易的是价格变化带来的盈亏。**

永续合约没有固定到期日，因此需要资金费率（Funding Rate）机制让合约价格尽量接近标的资产价格。当永续合约价格高于现货价格时，通常多头向空头支付资金费率，从而鼓励更多交易者做空；反之则空头向多头支付。dYdX 的机制也将资金费率用于推动永续合约价格向 Oracle Price 靠拢。

---

### 第四阶段：DeFi 协议组合化

随着 DEX、借贷和衍生品的发展，DeFi 开始形成更复杂的组合。

例如，一个用户可以：

```text
ETH
 ↓
存入借贷协议
 ↓
借出 USDT
 ↓
使用 USDT 购买其他资产
 ↓
继续参与 DEX 或衍生品交易
```

这也是 DeFi 的一个重要特点：**协议之间可以像乐高积木一样组合。**

一个协议提供流动性，另一个协议提供借贷，第三个协议提供衍生品。智能合约之间可以互相调用，从而组合出传统金融中更加复杂的产品。

因此，我认为 DeFi 的发展主线可以总结为：

```text
资产发行
   ↓
DEX / Swap
   ↓
流动性池
   ↓
借贷
   ↓
杠杆
   ↓
衍生品 / 永续合约
   ↓
多个协议组合
```

---

## ③ 回答：借贷和期货分别怎么实现

## 1. 借贷如何实现？

我认为一个最简单的链上借贷协议需要四个核心部分：

```text
存款
Borrow
抵押率计算
清算
```

### 第一步：用户存入资产

用户可以将 USDT、ETH 等资产存入 LendingPool：

```solidity
deposit(token, amount)
```

智能合约记录：

```text
用户地址
↓
存入资产数量
↓
获得利息凭证
```

这些资金形成协议的流动性池。

---

### 第二步：用户抵押资产并借款

用户不能无限制借款。

例如：

```text
抵押 ETH 价值：1000 USDT
最大抵押率：75%
```

那么用户最多可能借：

```text
750 USDT
```

智能合约需要通过价格系统计算：

```text
抵押品价值
=
抵押品数量 × 当前市场价格
```

然后检查：

```text
抵押品价值 × 抵押率 >= 借款价值
```

只有满足条件才允许借款。

---

### 第三步：计算健康程度

借贷协议需要持续关注用户的抵押品是否足够。

可以设计一个类似 Aave Health Factor 的概念：

```text
Health Factor
=
抵押品价值 × 清算阈值
/
债务价值
```

当：

```text
Health Factor > 1
```

仓位通常是安全的。

当：

```text
Health Factor < 1
```

说明抵押品已经不足以覆盖债务，可能触发清算。Aave 将健康因子作为判断借贷仓位风险和清算资格的重要指标。

---

### 第四步：清算

假设：

```text
用户抵押 ETH
借出 1000 USDT
```

之后 ETH 价格大幅下跌。

如果用户不补充抵押物，也不偿还部分债务，那么任何人都可以调用：

```solidity
liquidate(user)
```

清算人的逻辑大致是：

```text
清算人偿还用户部分债务
        ↓
协议减少用户债务
        ↓
清算人获得用户部分 ETH
        ↓
获得一定清算奖励
```

这样协议可以避免出现大量坏账。

所以我认为，借贷协议的核心并不是简单的“借钱”，而是：

**超额抵押 + 实时价格计算 + 健康度判断 + 自动清算。**

---

## 2. 期货 / 衍生品如何实现？

链上期货或永续合约比 Swap 更复杂，因为协议不能只依靠池子中的 Token 数量判断价格。

我认为至少需要四个核心机制：

```text
预言机
保证金
仓位管理
资金费率
```

### ① 预言机（Oracle）

期货合约需要知道 ETH、BTC 等资产的市场价格。

例如：

```text
ETH = 3000 USDT
```

这个价格不能让用户自己提交，否则用户可以故意上传错误价格。

因此需要 Oracle：

```text
Oracle
   ↓
向链上提供 ETH / USDT 价格
   ↓
合约计算用户盈亏
   ↓
判断是否清算
```

dYdX 使用 Oracle Price 来判断账户是否有足够抵押物，并用于清算和触发某些订单。

---

### ② 保证金（Margin）

用户开仓之前需要先存入保证金。

例如：

```text
存入 100 USDT
使用 10 倍杠杆
```

那么用户可以获得：

```text
1000 USDT 的 ETH 仓位
```

但用户实际上只存入了 100 USDT，因此价格出现较小波动就可能导致较大的收益或亏损。

智能合约需要记录：

```text
struct Position {
    address trader;
    bool isLong;
    uint256 margin;
    uint256 size;
    uint256 entryPrice;
}
```

例如用户以 3000 USDT 开 ETH 多单：

```text
entryPrice = 3000
```

当前价格变成：

```text
currentPrice = 3300
```

那么多单盈利。

如果变成：

```text
currentPrice = 2700
```

那么多单亏损。

---

### ③ 清算

当亏损不断扩大，保证金不足时，智能合约需要自动允许其他人进行清算。

逻辑类似：

```text
当前保证金 + 未实现盈亏
        ↓
账户权益
        ↓
是否低于维持保证金
        ↓
是
        ↓
允许清算
```

因此，衍生品协议和借贷协议一样，也非常依赖价格预言机和自动清算机制。

---

### ④ 资金费率（Funding Rate）

传统期货通常有到期日，但永续合约没有。

那么就需要一种机制让：

```text
永续合约价格 ≈ 现货价格
```

例如 ETH 永续合约价格高于 ETH 现货价格。

这意味着市场可能有太多用户做多。

协议可以设计：

```text
多头支付资金费率
        ↓
空头获得资金费率
```

这样会鼓励更多用户开空单，使永续合约价格逐渐回到合理范围。

反过来，如果合约价格低于现货价格：

```text
空头支付
        ↓
多头获得
```

dYdX 的资金费率机制正是用于激励交易者，使永续合约价格保持接近标的资产的 Oracle Price。

因此，一个简化的链上永续合约系统可以理解为：

```text
用户存入保证金
        ↓
开多 / 开空
        ↓
Oracle 更新市场价格
        ↓
智能合约计算盈亏
        ↓
检查维持保证金
        ↓
不足则允许清算
        ↓
通过 Funding Rate 调节多空市场
```

## ④ 展望：如果扩展我们的 DApp

如果让我在课程中的 Swap DApp 基础上继续扩展，我会优先选择增加一个简单的借贷功能，而不是直接实现完整的期货交易。

原因是我们现在已经有：

```text
ERC20 Token
DEX
Swap
Liquidity Pool
```

这些已经构成了一部分 DeFi 基础设施。

我会新增一个：

```text
LendingPool.sol
```

核心功能包括：

```solidity
depositCollateral()
borrow()
repay()
withdrawCollateral()
liquidate()
```

整体流程可以设计成：

```text
用户拥有 DLK
        ↓
抵押 DLK
        ↓
Oracle 获取 DLK 价格
        ↓
计算最大可借额度
        ↓
借出 mUSDT
        ↓
持续监控抵押率
        ↓
价格下跌
        ↓
触发清算
```

在技术上，我会增加以下模块：

### 1. PriceOracle 合约

负责提供：

```text
DLK / USDT
ETH / USDT
```

等资产价格。

在真正的生产环境中不能简单相信用户提交的价格，而应该使用可靠的预言机机制。同时，也可以参考 AMM 的时间加权平均价格（TWAP）设计来降低短时间价格操纵的风险。Uniswap 的相关设计正是通过累计价格数据构造 TWAP，以提高价格数据的抗操纵能力。

---

### 2. LendingPool 合约

负责：

* 用户存款
* 用户抵押
* 用户借款
* 用户还款
* 利息计算

---

### 3. RiskManager 合约

负责计算：

```text
Collateral Value
Debt Value
Health Factor
Liquidation Threshold
```

这样可以将金融风险逻辑和资产存储逻辑分开。

---

### 4. Liquidation 合约

任何人都可以检查危险仓位。

例如：

```text
if (healthFactor < 1) {
    allowLiquidation();
}
```

清算人偿还部分债务，然后获得对应抵押资产和奖励。

---

如果未来进一步扩展到期货，我会新增：

```text
Oracle
MarginVault
PositionManager
FundingRateManager
LiquidationEngine
```

大致结构为：

```text
Swap DApp
│
├── AMM / LiquidityPool
│
├── LendingPool
│     ├── Collateral
│     ├── Borrow
│     └── Liquidation
│
└── Perpetual Market
      ├── Margin
      ├── Position
      ├── Oracle
      ├── Funding Rate
      └── Liquidation
```

不过，我认为实际开发时不应该一开始就尝试实现完整的 dYdX。

更合理的路线是：

```text
第一步：完成 Swap
        ↓
第二步：加入简单 LendingPool
        ↓
第三步：加入 Oracle
        ↓
第四步：实现 Health Factor
        ↓
第五步：实现 Liquidation
        ↓
第六步：再尝试保证金交易和永续合约
```

通过这次研究，我最大的理解是：**DeFi 的发展其实就是不断把传统金融中的规则写成智能合约。**

Swap 解决的是资产交换问题；借贷解决的是资金使用效率问题；衍生品则进一步解决了杠杆、价格风险和市场预期的问题。

它们看起来是不同的产品，但底层有很多共同的技术基础：

```text
智能合约
+
Token
+
流动性
+
价格预言机
+
抵押
+
风险控制
+
清算
```

因此，我们课程中的 Swap 虽然只是一个简单的 DApp，但它实际上是进入更复杂 DeFi 世界的第一步。理解了 AMM、流动性池和 Token 之间的关系之后，就可以继续理解借贷、杠杆和链上衍生品等更复杂的金融协议。
