## 二、已修复

### 1. 自成交防护实现缺陷（高）

**位置**：`server/src/engine/orderbook.ts` 的 `match()`

**问题**：自成交防护在「当前最优价档位整个都是吃单者自己的挂单」时执行 `break outer`，**终止整轮撮合**，而不是跳过这一档继续匹配后面档位的人。

**影响**：只要用户在最优价有自己的挂单，他就再也吃不到后面档位别人的单 —— 一个安全控制被实现成了拒绝服务。这不是「拒绝自成交」，而是「拒绝一切成交」。

**复现**（修复前实测）：

```
alice 挂 卖 100 × 1     -> 占住卖一
bob   挂 卖 101 × 1     -> 卖二
alice 下单 买 105 × 1   -> 出价 105，跨过两档

修复前：fills = []（0 笔成交），alice 的买单原样挂回簿上
         —— bob 的 101 明明可以成交，却被整档跳过逻辑连坐
修复后：fills = [maker=bob, price=101, qty=1]，符合价格优先
```

**修复**：把「永远看 `prices[0]`」改成用下标 `pi` 遍历档位。档位内用 `k` 找到第一个「不是自己」的挂单并与之成交；若整档都是自己的单，则 `pi++` 跳过该档。被跳过的自持挂单**保持原排队位置**（不做移尾，避免改变它们的价格-时间优先次序）。每轮成交量取买卖双方剩余量的较小值，因此必然有一方被耗尽，不会死循环。

**回归测试**：`server/src/engine/orderbook.test.ts`
- `拒绝 self-trade：整档都是自己的单时跳过该档，继续吃下一档`（直接覆盖该缺陷）
- `拒绝 self-trade：同档混合时跳过自己的单，别人的单按时间优先`

### 2. `/auth/nonce` 的 nonce 表无界增长（中）

**位置**：`server/src/auth.ts`

**问题**：`nonces` 是一个 `Map<address, {nonce, expires}>`，但**只有「同一个地址发起登录」时才会删除条目**（成功删除、过期删除）。因此一个地址只要取了 nonce 却从不登录，它的条目就永远留在内存里。

`GET /auth/nonce?address=...` 是**无需认证**的公开接口，且 `address` 可以是任意合法格式的新地址。

**影响**：未认证的攻击者可以用不断变化的地址刷这个接口，往 Map 里塞永不回收的条目，直到进程 OOM。单条约数百字节，百万次请求即可占用数百 MB。这是一个纯内存耗尽的拒绝服务。

**复现**（修复前）：连续用 25 个不同地址请求 nonce，第 1 个地址的条目依然存活 —— 说明没有任何淘汰机制。

**修复**：
- 加入 `MAX_NONCES`（默认 10 000）上限与 `SWEEP_INTERVAL_MS`（30 秒）节流；
- 每次取 nonce 时按节流回收**已过期**条目；
- 若表已满且回收不出空间，则淘汰**最老**的条目（`Map` 保持插入顺序，首个 key 即最老）。

**残留风险（如实说明）**：上限是「有界」而非「不可达」。攻击者仍可在两次回收之间填满上限，把其他用户正在进行的登录挤出表（表现为需要重新点一次 Sign in）。选择「淘汰最老」而不是「返回 429 拒绝」，是因为后者更容易被用来单点卡死所有人的登录。彻底解决需要按 IP 限流，或在登录态改用无状态方案。

**回归测试**：`server/src/auth.test.ts`（新增文件，3 个用例）
- 超出上限时淘汰最老的
- 过期的 nonce 会被清理
- 同一地址重复取 nonce 只占一份

### 7. 重启回放重复扣款（高）—— 实测发现，已修复

**位置**：`server/src/routes.ts` 的 `onWithdrawBackfill()`、`server/src/chain.ts` 的 `backfill()`

**问题**：提现是「先扣链下余额，再让用户自己去调 `Vault.withdraw` 上链」。签发授权的那一刻，后端**拿不到 tx hash**，所以没法像充值那样用 `processed_events`（键是 `txHash:logIndex`）标记「这笔已经记过账」。

于是：链下扣款一次（实时），下次启动回放 `Withdraw` 事件时**又扣一次**。用户每重启一次服务端，提现过的钱就被多扣一遍。

这正是问题 3「服务端不保存任何待上链记录」的下游后果：问题 3 说的是用户不提交链上交易时钱会消失，这里说的是用户提交了、钱也到账了，链下仍会被重复扣。

**实测证据（Fuji 真机）**：

事后对账时，账本总额与「链上金库余额 + 做市虚拟注资」差了 **恰好 40 USDC**：

```
链上金库 USDC（实测 balanceOf）        = 7010
做市虚拟注资 MM_SEED_USDC              = 100000
应收敛到的账本总额                     = 107010
实际账本总额（各账户求和）             = 106970   ← 少了 40
```

而 40 恰好是最后一笔提现的金额（tx `0x14bc8b70…`）。同时：

- 这笔提现的事件 `0x14bc8b70…:1` **在** `processed_events` 里 → 说明回放确实处理过它并扣了账；
- 更早那笔 450 USDC 的提现 `0x1801b319…` **不在** `processed_events` 里 → 说明该次回放的起始游标已经越过它，它只被实时扣过一次。

两笔提现、一笔被扣两次、一笔被扣一次，差额正好 40，与账本缺口完全吻合。

**修复思路**：用后端自己生成的 `nonce` 来认领。`Vault.Withdraw` 事件本身带 `nonce`，而后端在 `/withdraw` 签发授权时就知道这个 nonce：

1. 新增 `debited_nonces` 表，`/withdraw` 里 `ledger.debit()` 成功后立刻 `markWithdrawn(nonce)`；
2. `chain.ts` 的回放把事件的 `nonce` 一并带给回调；
3. `onWithdrawBackfill()` 先查 `isWithdrawn(nonce)`：命中说明「这笔是本站实时扣过的」，只补 `processed_events` 标记、**不再扣账**；没命中（例如手工导入的历史账户）才照常扣。

这条路径和问题 3 的建议一致 —— 以 nonce 为键记录 pending 提现，只是本次只做到「防重复扣款」，**超时未上链自动退款仍未实现**（见 §三）。

**回归测试**：`server/src/store.test.ts`（新增 describe「重启回放提现：不能重复扣款」，3 个用例）

- 走**真实 HTTP 路径** `POST /withdraw` 扣一次账，关库、重开，再回放那笔 `Withdraw` 事件 → 余额必须仍是 60（不是 20）
- `nonce` 没见过的历史提现，回放照常扣账（保证原有语义不被修坏）
- 同一笔事件回放两次也只扣一次

> 把修复代码临时改回 `if (false)` 后，第 1 个用例立刻失败：`expected 2000000000n to be 6000000000n` —— 即余额被扣成 20，测试确实能抓到这个缺陷。

## 三、已报告、未修复

以下问题均为**设计层面**的取舍，修复会改变对外语义或需要重新部署合约，超出本次「修复一个真实问题」的范围，故只报告。

### 3. `/withdraw` 先扣账后签名（高）

**位置**：`server/src/routes.ts:217`

服务端在 `/withdraw` 里先执行 `ledger.debit(owner, asset, amount)`，再签发 EIP-712 授权返回给前端。**服务端不保存任何「待上链」记录**。

若用户在 MetaMask 里拒绝这笔交易、或直接关掉弹窗，链下余额已经被扣掉，而服务端没有任何凭据可以回滚它 —— 用户的这部分余额永久消失。授权本身 10 分钟后过期，过期后既不退款也不重签。

**建议**：服务端以 nonce 为键记录 pending 提现；监听 `Vault.Withdraw` 事件确认落链；对超时未落链的授权自动退款。仓库 README 已把它列为「已知简化」，但它在真实环境里是直接的资金损失路径。

> 2026-09-23 补充：问题 7 的修复走了上面建议的第一步 —— `debited_nonces` 表已经按 nonce 记下了「这笔提现扣过账」。但**超时未落链自动退款**仍然没做，所以本条维持「未修复」。

### 4. 链下余额无链上背书（高）

**位置**：`server/src/index.ts:81-82`（`MM_SEED_USDC` / `MM_SEED_WAVAX`）

做市账户的启动资金是**虚拟注资**，没有对应的链上 `deposit`。用户与做市账户成交后，账本里凭空多出的那部分币在链上是没有抵押的。

当用户提现时，`Vault` 支付的是**其他用户真实充进来**的币。一旦链下总债权超过金库存量，最后一个提现者的 `IERC20.safeTransfer` 会因余额不足 revert —— 而此时他的链下余额已经按问题 3 扣掉了，钱既没上链也没退回账本。

**建议**：链上模式下把 `MM_SEED_*` 置 0，让做市账户真实 `deposit`；或在 `Vault` 内实现链上余额硬上限（本次作业的进阶项之一）。

### 5. `JWT_SECRET` 有可用默认值（高）

**位置**：`server/src/index.ts:20`

```ts
const JWT_SECRET = env.JWT_SECRET ?? "dev-secret-change-me";
```

未设置该环境变量时服务端会静默使用公开的默认密钥。JWT 是 HS256，算法已固定（`verifyToken` 传了 `algorithms: ["HS256"]`，不存在 alg 混淆），但**密钥公开 = 任何人都能为任意地址伪造合法 JWT**，进而调用 `/balances`、`/orders`、`/withdraw` 把别人的余额提走。

**建议**：链上模式下若检测到默认密钥则拒绝启动（fail fast），而不是打日志了事。

### 6. 缺少频率限制（低）

`/auth/nonce`、`/orders`、`/dev/faucet` 均无频率限制。`/dev/faucet` 仅在离线模式开放，风险有限；但登录和下单接口在公网演示时容易被刷。建议按 IP 做令牌桶限流。

## 四、未发现问题的部分（已验证）

以下是我重点核对后**确认没有对不上**的地方，一并记录以免重复排查：

- **EIP-712 登录域一致性**：前端 `web/src/lib/useAuth.ts` 与后端 `server/src/auth.ts` 的 domain（`MiniDex` / `1` / chainId）、types、statement（`Sign in to MiniDex`）逐字段一致；domain 用的是后端 `/config` 下发的 chainId 而非钱包当前链，避免了切链后登录失败。
- **提现签名域一致性**：`server/src/chain.ts` 与 `Vault.sol` 的 domain（`MiniDexVault` / `1` / chainId / verifyingContract）和 typehash 完全一致；合约侧有 `test_HashWithdraw_MatchesManualEip712` 手工拼 EIP-712 **交叉验证**，`test_RevertWhen_Withdraw_CallerIsNotUser` 覆盖了「拿别人的合法签名去提」的场景（digest 里 user 取 `msg.sender`，等价于身份绑定）。
- **提现重放**：`usedNonces` 全局去重 + `deadline` 过期 + `ECDSA.recover` 校验 signer；`test_RevertWhen_Withdraw_ReplaySameNonce` 已覆盖。
- **资金守恒**：下单冻结 → 成交划转 → 剩余解冻，账本 `available`/`locked` 恒等式有 `ledger.test.ts` 覆盖；`ReentrancyGuard` + `SafeERC20` 覆盖了合约侧的重入与异常 ERC20。
- **地址大小写**：账本统一 `norm()` 转小写存取，避免了同一个钱包因大小写不同被当成两个账户。
